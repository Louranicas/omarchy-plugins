# Configured adapter cancellation and explicit replacement

The runtime retains the existing lifecycle: cancel pending permissions, notify the adapter, wait for completion, then close/TERM/KILL if the cancellation deadline expires. `ReapReceipt::Reaped` reports actual direct-child reap; a close request, signal or outstanding receipt is not equivalent. Worker/Transport owns child cleanup immediately after spawn and retains custody if a test or caller unwinds.

`tests/recovery.rs` reads a private explicit provider profile and starts only a local Python ACP fixture. Cooperative cancellation sends permission cancellation before `session/cancel`, drains late text/permission requests without approving them, and allows a new turn with a fresh permission epoch. An unresponsive fixture ignores cancellation and TERM; logical deadline advancement drives escalation while actual OS process disappearance and reap are checked. A separate live fixture remains usable, demonstrating process cleanup does not kill that unrelated session.

After confirmed reap, the test explicitly constructs another Worker from the same frozen profile and rechecks preflight. The new runtime Instance differs even though generation, first-turn epoch, provider session ID and permission wire ID are reused. An answer captured from the old Instance is rejected while the new permission remains pending. The current answer succeeds. No old transcript or pending permission is replayed.

This is fresh Worker construction, not `ask-core::Session::restart`, which has its own prior-reap/generation contract. It is also not a configured UI restart action. The managed UI has no restart command; a future recovery flow must establish new command/view ownership and actual managed admission/fence rather than reusing old queued commands or an old admission boolean. A runtime Instance does not grant a modal lease.

Evidence is synthetic: no credentials, paid requests, vendor compatibility or host configuration is involved. Each test polling loop checks a two-second absolute deadline between pump calls; a pump or kernel operation can finish after that deadline, so this is not a strict wall-time bound; fixture processes have a ten-second alarm and transport custody. Logical clock advancement tests escalation decisions, not real five-second latency or hard realtime guarantees. Direct-child reap does not prove every descendant was reaped. Existing provider path-to-exec and same-user limitations remain unchanged. Run `cargo test -p ask-runtime --test recovery`; Python3 is required.
